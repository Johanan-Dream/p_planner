# PRD — P형 여행자를 위한 오사카 여행 플래너

> **핵심 콘셉트:** 계획은 귀찮아도, 여행은 알차게!
>
> **문서 유형:** Product Requirements Document (PRD)  
> **버전:** MVP v1.0  
> **대상 지역:** 일본 오사카  
> **제품 형태:** 모바일 우선 반응형 웹 애플리케이션  
> **개발 도구:** Replit AI

---

## 1. 프로젝트 개요

### 1.1 배경 및 문제 정의

오사카 자유여행을 준비하는 여행자는 방문하고 싶은 장소가 있더라도 관광지별 운영시간, 휴무일, 예약 필요 여부를 일일이 확인하고 이동 동선을 직접 설계해야 한다. 특히 계획을 세우기 귀찮아하거나 즉흥적인 여행을 선호하는 사용자는 이 과정에 큰 부담을 느낀다.

### 1.2 제품 목표

여행 날짜와 방문하고 싶은 관광지만 선택하면, 서비스가 관광지의 방문 가능 여부를 검토하고 사용자의 **무계획력(0~100%)** 에 맞춘 날짜별 여행 일정과 이동 동선을 생성한다.

**핵심 원칙:** AI가 방문 장소를 일방적으로 추천하는 것이 아니라, **사용자가 직접 선택한 관광지를 중심으로 실제 방문 가능한 일정을 구성**한다.

### 1.3 대상 사용자

- 오사카 자유여행을 준비하는 국내 여행자
- MBTI P형처럼 세밀한 여행 계획 수립을 부담스러워하는 사용자
- 가고 싶은 곳은 정했지만 운영정보와 이동 동선을 직접 조사하기 어려운 사용자
- 필수 방문 장소만 정해두고 나머지는 유연하게 여행하고 싶은 사용자

### 1.4 핵심 차별점

1. 최소 입력으로 여행 계획 시작
2. 무계획력에 따른 일정 밀도 및 자유시간 자동 조절
3. 사용자가 지정한 **필수 관광지** 우선 반영
4. 운영시간·휴무일·예약 필요 여부의 사전 검증
5. Google Maps 기반 이동 동선 시각화
6. 계획 변경 시 간편한 일정 수정 및 재구성

## 2. 기술 및 개발 환경

| 구분 | 기술/도구 |
|---|---|
| 개발 환경 | Replit AI |
| 서비스 형태 | 모바일 우선 반응형 웹 |
| 프론트엔드 | React + TypeScript |
| 스타일링 | Tailwind CSS |
| 지도 | Google Maps JavaScript API |
| 장소 검색 및 정보 | Google Places API |
| 이동 경로 및 소요시간 | Google Maps Routes API |
| 관광지 데이터 | 오사카 주요 관광지 초기 데이터 + 외부 API |
| AI | Replit 환경에서 사용 가능한 AI 연동 방식 |
| 초기 데이터 저장 | 브라우저 Local Storage |

### 2.1 개발 원칙

- 외부 API 키는 환경변수로 관리한다.
- Google Maps API 키가 없어도 여행 설정과 샘플 관광지 선택 기능은 사용할 수 있어야 한다.
- 지도 및 경로처럼 API 의존성이 있는 기능에는 **연동 필요/설정 상태**를 명확하게 표시한다.
- 실제 API 데이터와 샘플 데이터를 명시적으로 구분한다.
- 확인되지 않은 운영정보, 예약 마감일 또는 방문 가능 여부를 AI가 임의로 생성하지 않는다.
- API 오류가 발생하더라도 전체 앱이 중단되지 않도록 한다.

## 4. 상세 기능 요구사항

### 4.1 화면 1 — 여행 설정

**목적:** 최소한의 입력으로 여행의 기본 조건을 수집한다.

**입력 항목**

- 여행 시작일
- 여행 종료일
- 무계획력(0~100%) 슬라이더

**무계획력 구간**

| 범위 | 여행 스타일 | 일정 생성 방향 |
|---|---|---|
| 0~30% | 계획형 | 상대적으로 촘촘한 일정 |
| 31~70% | 균형형 | 주요 관광과 휴식·자유시간의 균형 |
| 71~100% | 즉흥형 | 필수 관광지 위주, 자유시간 확대 |

**슬라이더 문구 예시**

- 20%: “계획이 있어야 마음이 편한 타입!”
- 50%: “계획도 좋지만 즉흥 여행도 좋아!”
- 90%: “일단 비행기부터 타고 생각하자!”

**동작 및 검증**

- 종료일은 시작일보다 빠를 수 없다.
- 무계획력 조정 시 현재 스타일 설명을 즉시 갱신한다.
- 이전 단계로 돌아와도 선택값을 유지한다.
- 하단에 **관광지 선택하기** 버튼을 배치한다.

### 4.2 화면 2 — 관광지 선택 및 방문 가능 여부 확인

**목적:** 사용자가 방문하고 싶은 장소를 선택하고 방문 관련 제약을 사전에 파악한다.

**기능 요구사항**

- Google Places API 기반 관광지 이름 검색 및 자동완성
- 초기 관광지 카드 목록 제공
- 장소 선택/선택 취소
- 선택한 관광지 개수 표시
- 관광지별 **꼭 가야 하는 곳** 지정/해제
- 운영시간, 정기 휴무일, 예약 필요 여부 표시
- 예약 마감일 또는 예약 가능 기간 표시(검증된 경우에 한함)
- 여행 날짜와 운영정보 비교를 통한 방문 가능 여부 표시
- 운영정보 충돌 시 해당 장소 제외 또는 다른 날짜 배치 안내

**관광지 카드 필드**

| 필드 | 설명 |
|---|---|
| 사진 | 관광지 이미지 |
| 이름 | 관광지명 |
| 설명 | 간단한 관광지 소개 |
| 운영시간 | 확인 가능한 영업/방문 가능 시간 |
| 휴무일 | 확인 가능한 정기 휴무일 |
| 예약 상태 | 필요/불필요/확인 필요 |
| 필수 방문 | 토글 버튼 |
| 추가 | 관광지 선택/선택 취소 버튼 |

**방문 상태**

| 상태 | 판정/표시 원칙 |
|---|---|
| 방문 가능 | 여행 날짜 및 확인된 운영정보상 방문 가능한 시간이 존재함. 예약 확정을 의미하지 않음 |
| 휴무일 충돌 | 확인된 휴무일과 여행 일정이 충돌함 |
| 예약 확인 필요 | 예약 필요 여부 또는 예약 가능 상태를 추가 확인해야 함 |
| 운영정보 확인 필요 | 운영시간이나 휴무일 등 핵심 정보가 누락되었거나 신뢰할 수 없음 |

> **중요:** Google Places API는 관광지별 예약 필요 여부나 예약 마감일을 완전하게 제공하지 않는다. 위치·주소·운영시간 등 제공되는 장소 정보는 Places API에서 가져오고, 예약 관련 정보는 별도 관광지 데이터로 관리한다. 확인되지 않은 예약 마감일은 만들지 않고 **“공식 예약 사이트 확인 필요”** 로 표시한다.

**하단 CTA:** **선택 완료하고 동선 만들기**

### 4.3 관광지 상세 팝업

관광지 카드 클릭 시 열리는 상세 팝업이다.

**표시 항목**

- 관광지 이름 및 사진
- 주소
- Google Maps 위치
- 운영시간 및 휴무일
- 예약 필요 여부
- 예약 마감일 또는 예약 가능 기간(확인된 경우)
- 공식 홈페이지 링크
- 정보 출처 및 마지막 확인일

Google Places API 정보와 별도 예약 데이터의 출처를 구분할 수 있어야 한다. 확인되지 않은 값은 **확인 필요**로 표시한다.

### 4.4 화면 3 — 날짜별 여행 일정표 및 지도

**목적:** 사용자가 선택한 장소로 구성된 방문 일정과 실제 이동 동선을 확인하고 편집한다.

**기능 요구사항**

1. 날짜별 일정표 자동 생성
2. 관광지 방문 순서 자동 배치
3. 예상 체류시간 표시
4. 장소 간 예상 이동시간 표시
5. Google Maps 지도 표시
6. 방문 순서에 따른 번호 마커 표시
7. 실제 도로 기반 이동 경로 연결
8. 무계획력에 따른 자유시간 확보
9. 필수 방문 관광지 우선 배치
10. 순서·날짜·관광지·무계획력 수정 및 재생성
11. 운영시간·예약·이동 제약 충돌 경고

#### 4.4.1 일정 생성 규칙

- 사용자가 선택하지 않은 관광지를 임의로 일정에 추가하지 않는다.
- 필수 방문 장소를 우선 배치하되, 실제 방문 가능 조건을 위반하지 않는다.
- 관광지 운영시간, 휴무일 및 여행 날짜를 고려한다.
- 장소 간 이동 거리·예상 이동시간을 고려한다.
- 관광지별 예상 체류시간을 반영한다.
- 무계획력에 따라 일일 일정 밀도와 자유시간을 조절한다.
- 하루 안에 소화하기 어려운 장소를 무리하게 배치하지 않는다.
- 충돌이 발생하면 이유와 해결 가능한 조치를 표시한다.
- 방문 가능 여부가 미확인인 장소는 확정 일정처럼 표시하지 않는다.
- 선택한 장소 중 배치하지 못한 관광지는 이유와 함께 별도로 보여준다.

#### 4.4.2 무계획력 반영 방식

| 예시값 | 일정 구성 |
|---|---|
| 20% | 방문 순서와 시간을 비교적 촘촘하게 배치 |
| 50% | 주요 관광지를 배치하고 휴식 및 자유시간 확보 |
| 90% | 필수 관광지만 우선 확정하고 나머지 시간은 자유시간으로 유지 |

무계획력은 장식용 UI가 아니라 **일정 생성 엔진의 실제 입력값**이다. 구간별 자유시간 배정량, 하루 방문 장소 수, 일정 사이의 완충시간에 영향을 주어야 한다. 세부 계수는 초기 구현에서 설정 가능한 상수로 분리해 사용자 테스트를 통해 조정한다.

#### 4.4.3 Google Maps 연동

- 선택한 관광지 위치에 마커 표시
- 날짜별 방문 순서에 따라 번호 표시
- Google Maps Routes API를 활용한 지원 가능한 도보 경로 계산 및 지도 표시
- 날짜별 경로 구분
- 마커 클릭 시 장소명과 방문 예정 시간 표시
- 지도 확대/축소
- 일정표에서 장소 선택 시 해당 지도 마커 강조
- 일정 수정 시 경로 재계산 및 지도 갱신
- 대중교통 경로는 지원 여부를 확인한 뒤 후속 구현

API에서 지원하지 않거나 계산에 실패한 경로를 실제 경로처럼 표시하지 않는다.

#### 4.4.4 경로 최적화

**최적화 입력**

1. 관광지 간 이동 거리
2. 예상 이동시간
3. 관광지 운영시간
4. 예상 체류시간
5. 필수 방문 여부
6. 여행 날짜
7. 무계획력 설정

**처리 원칙**

- Routes API로 이동시간 및 이동 경로를 조회한다.
- **일정 배치 로직은 Routes API와 별도로 구현**한다.
- 가까운 장소만 연결하지 말고 시간 제약과 체류시간을 반영해 방문 가능한 순서를 탐색한다.
- 필수 방문 장소를 우선 고려하되 제약 충돌을 숨기지 않는다.
- 배치에 실패한 장소는 사유를 사용자에게 알려준다.

#### 4.4.5 일정 수정

- 방문 순서 변경
- 관광지 삭제
- 관광지를 다른 날짜로 이동
- 무계획력 변경
- 일정 재생성

수정이 발생하면 일정표·예상 시간·충돌 상태·지도 경로를 일관되게 갱신한다.

## 5. UI/UX 가이드

### 5.1 비주얼 방향

- 귀엽고 친근하지만 깔끔한 일본 여행 서비스 분위기
- 모바일 우선 반응형 디자인
- 화이트 베이스 + 밝고 부드러운 파스텔 컬러
- 둥근 카드와 버튼, 직관적인 아이콘
- 관광지 사진을 통한 빠른 장소 인지
- 단계별 진행으로 복잡한 입력 최소화

### 5.2 UX 원칙

1. 사용자가 고민해야 할 선택을 최소화한다.
2. 복잡한 운영정보를 한눈에 이해할 수 있도록 상태로 요약한다.
3. 예약·휴무일 충돌과 확인 필요 상태를 눈에 띄게 표시한다.
4. 사용자가 선택한 관광지 및 필수 방문 설정을 존중한다.
5. 이전 단계로 이동해도 입력값을 유지한다.
6. 모바일에서도 지도와 일정표를 편리하게 탐색하게 한다.
7. 샘플 데이터와 실제 데이터, 확인된 정보와 미확인 정보를 명확히 구별한다.

### 5.3 화면 3 레이아웃

**데스크톱:** 왼쪽 날짜별 일정표 / 오른쪽 Google Maps 지도

**모바일:** 상단 날짜 선택 / 중앙 Google Maps 지도 / 하단 드래그 가능한 일정표 패널

**데이터 통합 원칙**

- Google Places API 데이터와 별도 관리하는 예약·특별 휴무 데이터를 결합할 수 있도록 분리 설계한다.
- 예약 필요 여부 등의 미확인 필드는 `null` 또는 `unknown`으로 관리한다.
- 확인되지 않은 정보는 자동 추측·생성하지 않는다.
- 데이터 출처 및 확인일을 필드별로 추적할 수 있도록 확장 가능하게 구성한다.

## 7. API 및 데이터 처리 정책

### 7.1 Google Maps JavaScript API

- 지도 렌더링
- 관광지 마커 표시
- 마커 상호작용 및 지도 카메라 제어

### 7.2 Google Places API

- 관광지 검색 및 자동완성
- 주소·위치·운영시간 등 API가 제공하는 장소 정보 조회
- API가 제공하지 않는 정보는 별도 데이터로 취급

### 7.3 Google Maps Routes API

- 지원되는 이동 수단의 실제 경로 계산
- 예상 이동시간 및 거리 조회
- 도보 이동 우선 구현
- 대중교통 지원 범위는 사전 확인 후 도입 여부 결정

### 7.4 예약 정보

- 예약 필요 여부, 예약 마감일, 예약 가능 기간, 특별 휴무일은 별도 데이터에서 관리
- 정보 출처와 마지막 확인일 유지
- 실시간 예약 조회 불가 시 **공식 예약 사이트 확인 필요**로 안내
- 실제 예약·결제 및 잔여석 조회는 MVP 범위에서 제외

### 7.5 API 키 및 과금 관리

- API 키는 환경변수로 관리한다.
- 서버 전용 키는 클라이언트에 노출하지 않는다.
- 브라우저에서 사용하는 지도 키에는 HTTP 리퍼러 제한을 적용한다.
- 각 키의 API 사용 권한은 필요한 API로 제한한다.
- 불필요한 API 호출을 줄이고 동일 정보의 반복 조회를 방지한다.
- API 이용약관 및 캐싱 제한을 준수한다.
- Google Maps Platform의 사용량·예산·과금 모니터링 방법을 안내한다.
- Replit Runtime 크레딧과 Google Maps API 사용료는 별개로 관리한다.

### 7.6 폴백 및 오류 처리

- **API 키 없음:** 여행 설정·초기 관광지 샘플 선택을 제공하고, 지도·실제 경로는 연동 필요 상태로 표시
- **Places API 오류:** 사용 가능한 초기 장소 데이터를 보여주되 샘플/캐시 여부 명시
- **Routes API 오류:** 기존 일정이 있더라도 실제 이동시간·경로를 검증하지 못했다는 경고 표시
- **데이터 누락:** 추정치로 채우지 않고 확인 필요 상태 노출
- **오프라인/네트워크 문제:** 저장된 여행 설정을 유지하고 재시도 옵션 제공

## 10. MVP 완료 기준 및 인수 테스트

### 10.1 핵심 시나리오

- [ ] 사용자가 오사카 여행 시작일과 종료일을 설정할 수 있다.
- [ ] 무계획력을 **80%**로 설정할 수 있다.
- [ ] 관광지 **5개**를 선택할 수 있다.
- [ ] 그중 **2개**를 필수 방문으로 지정할 수 있다.
- [ ] 관광지별 운영정보와 예약 필요 여부를 확인할 수 있다.
- [ ] 방문 불가능하거나 확인이 필요한 관광지에 적절한 경고가 표시된다.
- [ ] **동선 만들기**를 누르면 날짜별 일정표가 생성된다.
- [ ] 필수 관광지가 우선 고려되고 자유시간이 확보된다.
- [ ] Google Maps 연동이 설정된 환경에서 마커와 실제 이동 경로가 표시된다.
- [ ] 관광지 순서를 변경하면 일정표와 지도 경로가 함께 갱신된다.

### 10.2 추가 검증 조건

- [ ] 운영시간·휴무일을 알 수 없는 장소를 확정 방문 가능으로 표시하지 않는다.
- [ ] 확인되지 않은 예약 마감일을 임의 생성하지 않는다.
- [ ] 일정에 들어가지 못한 장소와 그 이유를 확인할 수 있다.
- [ ] 이전 화면으로 돌아가도 입력·선택 내역이 보존된다.
- [ ] API 키가 없더라도 여행 설정 및 샘플 관광지 선택은 정상 작동한다.
- [ ] API 오류가 발생해도 앱이 종료되지 않고 적절한 메시지를 제공한다.
- [ ] 모바일 및 데스크톱에서 주요 사용자 흐름이 정상 작동한다.
- [ ] 주요 버튼과 화면 이동은 모두 실제 동작하며 단순 정적 목업이 아니다.

**완료 판정:** 핵심 시나리오가 통과하고, Google Maps API가 정상 설정된 환경에서 실제 경로가 표시되며, 미확인 데이터에 대한 잘못된 확정 정보가 생성되지 않아야 한다.

## 11. Replit AI 개발 지시사항

1. 구현 전에 프로젝트 폴더 구조, 화면, 공통 컴포넌트 및 데이터 모델을 설계한다.
2. 전체 사용 흐름을 실행할 수 있는 MVP를 우선 구현한다.
3. **관광지 데이터 / 일정 생성 엔진 / Google Maps API 연동**을 별도 모듈로 분리한다.
4. 외부 API 키가 없으면 샘플 데이터로 기능 개발을 진행하되 실제 API 연동이 필요한 기능은 명시한다.
5. 확인되지 않은 운영정보, 예약 마감일, 예약 가능 여부를 생성하지 않는다.
6. API 장애·사용량 제한·네트워크 문제를 처리하고 앱 전체가 중단되지 않도록 한다.
7. 모바일과 데스크톱에서 반응형 레이아웃 및 상호작용을 검증한다.
8. 핵심 인수 테스트를 수행하고 발견된 문제를 수정한다.

### 11.1 권장 모듈 구성

```text
src/
  components/      # 공통 UI, 관광지 카드, 상세 팝업, 지도 패널
  pages/           # 여행 설정, 관광지 선택, 일정/지도
  data/            # 초기 관광지 데이터, 샘플 데이터
  services/        # Google Places, Maps, Routes API 호출
  planner/         # 방문 가능 여부 검증 및 일정 생성 알고리즘
  types/           # 관광지, 여행 설정, 일정 등 TypeScript 타입
  hooks/           # 상태 관리 및 데이터 조회 훅
  utils/           # 날짜/시간 계산 및 표시 유틸리티
```

구체적인 파일 구조는 Replit 프로젝트 환경에 맞춰 조정할 수 있으나, 데이터·계획 알고리즘·지도 연동의 책임 분리는 유지한다.
